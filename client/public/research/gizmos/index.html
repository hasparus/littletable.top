What earns a place in the marketplace?

A link-only fork lets Mira hand her deck to a friend tonight. A curated shelf makes good forks discoverable and gives Little Table a review queue. Open publishing lets strangers surprise each other and calls for reporting, delisting and a way to disable a harmful release. All three can carry the original creator, fork author, remix license and exact parent edition.

Publishing should copy the definition and redistributable assets. The party’s private readings, shuffle order and provider credentials belong to the session or author. An owner installs a specific edition after seeing its behavior and requested access. Another author publishing a revision should never silently change tonight’s game.

My first playtest would be a handoff. Give one player the official deck and ask them to make a reading another table wants. Can that owner explain the change before installing it? Do they want to pass it on after playing? That tests the reason to build a marketplace while leaving its publishing model open.

Open design question

Three ways to build the ferryman’s clock

Suppose the ferryman wakes after two character moments. Only the GM can mark a moment, but everyone can see the water rise. What should the GM be able to change when the next session takes a different turn?

A. Configure a tool during play

The GM picks a first-party clock, sets its length to two, and chooses who can tick it. On a phone this could take three taps. The team owns rendering, accessibility and upgrades. A request to draw a different kind of prop becomes product work.

Security cost. Fixed controls keep the permission surface small. The room still needs to reject unauthorized ticks, and reconnections must preserve the correct count. First experiment. Give a GM a two-segment dial midway through a scene. Watch whether they can configure it without interrupting the conversation. The case for this path is strongest if several tables want the same tool with different settings.

B. Fork a recipe and teach it a house rule

The GM copies a tracker and links two existing actions: mark a character moment and advance the clock. An agent can edit the recipe and rehearse it with sample players. The validated catalog supplies the controls. Inventing a new gesture or drawing surface would require a catalog extension.

Security cost. A valid recipe can still request an unwanted privilege. Show the owner exactly which player actions change, pin the reviewed revision, and authorize each action in the room. First experiment. Try the duet recipe, then ask three GMs for one variation each. Count how many they can express with existing actions and how often they correctly predict the player experience. Try the recipe workbench

C. Let an agent build a little application

The GM sketches a tide chart on which players place lanterns. A coding agent could build the gesture, artwork and rules in a disposable workspace. A reusable blueprint lets another GM take the code into their own game with fresh state. This gives unusual table rituals room to become genuinely new software. It also makes Little Table responsible for hosting, compatibility, recovery and resource costs.

Security cost. Generated code introduces an execution boundary. Give the draft synthetic data and narrow bindings, meter computation and outbound access, and keep a host-controlled pause and rollback path. First experiment. Commission one prop that the catalog cannot express. Measure authoring time, startup latency and recovery after a stalled rule before offering it to a second table. Where I lean, and what would change it

I’d personally prototype B first if the question is whether owners enjoy remixing tools. The duet took one recipe file and yielded an observable change from both seats. That trial establishes feasibility for one brief; it tells us little about demand. If the goal is helping a GM keep a scene moving tonight, A has the shorter path to a useful test. If the ambition is to let tables invent entirely new interfaces, C directly tests that ambition. I’d bring one real house rule from your table to the next conversation and see which approach gives it enough room.

Possible implementation for the recipe approach

Install and undo

On install, show the panel preview, author, definition version and actions that guests may take. Store the validated definition and its digest on the table. An edited or updated definition gets a new revision and an explicit owner confirmation. Preserve state on compatible upgrades. Refuse incompatible updates until the owner chooses a migration or reset. Pausing leaves the state intact. Removing a Gizmo removes its instance from that table.

One authoritative transition

Reuse the standalone owner session and CSRF checks for installation. For play, send the room a typed intent with an instance ID, expected revision and request ID. The room authenticates the actor, checks the role and current definition, deduplicates retries, applies one transition and broadcasts the committed revision. A stale click gets the current state. Two players passing simultaneously must produce one advance from the old revision. The browser role switch in the workshop is a local simulation of this contract.

Keep the two rooms separate

Mount the panel beside the existing board controls. Route a public Gizmo action only through the shared BoardRoom. A future GM-only Gizmo should live wholly in the owner’s separate secret room. A hidden field in shared JSON still reaches everyone with the shared pass. Keep player names, secret data, image URLs and room credentials out of extension inputs unless an approved action explicitly requires a narrow projection.

When to expand the API

Have three GMs build a spotlight tracker and adapt it for their own table. Watch whether they can predict who can press each button, fix a failed edit and recover the old version. Then ask for a tool the catalog cannot express. A reusable missing action argues for extending the catalog. A rule requiring genuinely novel computation is a candidate for an isolated runtime.

Release gates

  • Replaying a request after reconnect produces one state change. Concurrent stale requests converge on the same revision.
  • An owner can pause a broken Gizmo and open the board normally. A guest cannot install, edit or retrieve GM-only state.
  • Unknown catalog versions and malformed definitions leave the previous working install in place. Measure render and action latency on a phone with several panels before setting production limits.

Security judgment

What could hurt a real table?

My main concern is an ordinary-looking Gizmo gaining the GM’s authority. A spoiler sent to a player cannot be taken back. An agent can author a draft with sample data; installing it and reading the secret layer are separate privileges.

A copied clock spoils the ambush

A GM shares a clock face. Its title is public, but its trigger names the hidden traitor. If both fields travel to every client, hiding the trigger in the UI is too late. The shared room should receive only the public projection. The private room keeps the trigger. Release test: inspect a guest’s initial sync, reconnect data and export. None may contain the private fixture string.

A minor update changes who can act

An agent edits a label and also broadens advance from owner to table. The owner may miss that in a JSON diff. Pin the installed revision and display the behavioral change in plain language. Bind approval to its content digest and base revision. The room must check the actor on every action even if the button is disabled. Release test: a guest submitting an owner action directly leaves the queue untouched, and editing a reviewed draft invalidates its approval.

A broken rule stalls the session

A malformed recipe or expensive program can consume the room’s time while everyone waits. Keep catalog actions bounded. If arbitrary code becomes necessary, give it a separate invocation, a deadline, explicit resource limits and no ambient room credentials or outbound network. The room validates the proposed result. Release test: a timed-out rule leaves its last good state intact; the next player can still draw and the owner can pause the Gizmo.

What is proven today? The tab demo demonstrates the interaction and rejects unsupported rules. The local Wasm trial terminates one runaway fixture. Neither establishes guest isolation across clients, safe handling of arbitrary uploads or a production memory ceiling. Those are shipping gates for the corresponding capability.

Comparative report

What an install gives the table

Three decisions recur across the platforms: who installs a tool, where it runs, and who authorizes its effects. A single “enable mods” switch would collapse all three.

Room-level installation

Owlbear Rodeo lets a user add an extension by manifest URL and enable it per room. An extension can open an iframe popover and contribute tools through the SDK. Foundry separates installing a module from activating it for a game world. Its modules can load JavaScript, and a GM can deactivate modules together when diagnosing a broken world.

Borrow for Little Table Keep a library of packages and an independent install record on each table. Give the owner a way to open a board with all Gizmos paused.

Owlbear installation · Manifest reference · Foundry module management · Foundry module API

Host-rendered UI

Shopify checkout extensions contribute UI at named targets. The target determines the available data and operations. In json-render, the application defines a catalog of components and actions, then supplies their implementations through a registry. A JSON description can compose a control without bringing its own DOM or rendering code.

Borrow A catalog can be an optional authoring aid for stock controls. A schema can establish that “pass” is a valid action. The table service must still decide whether this particular player may invoke it.

Checkout extension API · json-render catalog · Registry

A separate runtime

Figma gives plugin logic a sandbox with a document API and allows an optional browser iframe for UI. Messages connect the two. VS Code can load declarative contributions without running extension code. Web extensions execute in a browser worker, where fetch is available. Moving work off the UI thread alone does not confine its network access.

Borrow Treat the Gizmo's inputs and proposed actions as an explicit protocol. Keep board passes, the editor object and the secret-layer store outside it.

Figma runtime · VS Code web extensions

Full application trust

Obsidian asks the user to leave Restricted Mode to run community plugins. An enabled plugin has the app’s access, including files and the network. A personal vault has a single decision-maker. At a shared table the installer can invite people who have never inspected the extension.

Decision An owner's installation should grant capabilities on that table. Guests should not have to run code with access to their browser session to sit down and play.

Obsidian plugin security

Hosted user code

Cloudflare Dynamic Workers can execute developer-supplied code with explicit service bindings, network egress policy and CPU and subrequest limits. An isolate with the host's default network policy may still make outbound requests. Cloudflare also distinguishes local Miniflare development from hardened execution.

Later experiment Start an isolated invocation with no outbound network and only a frozen projection of one Gizmo’s state. Accept a small, validated proposal in return. Measure cold start, invocation cost and termination under load before choosing a service.

Authoring environments

Ask the table to change

A GM should be able to point at a working Gizmo and describe how tonight’s table plays. The agent needs a copy it can edit, a table it can rehearse on, and a way to hand the result back to the owner.

Cloudflare OS makes the application itself editable

Cloudflare OS treats a Gadget as a shareable application backed by a Durable Object. Its coding agent builds and tests Gadgets. Sharing a Blueprint lets someone take a copy of the code and change it independently. Gatekeepers mediate access to specific external resources and can simulate side effects for review. This offers two distinct Little Table interactions: invite a player to tonight’s tracker, or give another GM a recipe they can fork with a fresh roster and empty clock. Cloudflare OS architecture

Where a coding agent works

E2B exposes a Linux VM lifecycle for agents, including pause, resume and termination. That is useful for running a compiler, package tools or browser tests across several authoring sessions. Cloudflare OS can also connect an existing GitHub repository. A repository-backed workflow gives maintainers a diff and review history. A GM at the table needs a working preview and a readable account of what changed. Both can refer to the same immutable revision. E2B sandbox lifecycle · Repository-backed work in Cloudflare OS

A workshop for one Gizmo

  1. Fork. Copy the installed definition and rule into a private draft. Give the agent the catalog, its version and synthetic player data. Keep the live room token and GM notes outside the workspace.
  2. Rehearse. Let the agent edit files, run acceptance tests and render the draft in a disposable table. Run one trace as the owner and one as a player. A rejected edit should leave the game in progress.
  3. Adopt. Show the behavioral diff, requested permissions and any state migration. The owner can apply that exact revision, discard it or keep it as a separate Gizmo. Changing a running instance should require a matching base revision.

Build choice. The manifest editor and a disposable preview are sufficient for catalog-backed tools. Add a resumable coding VM when authors need third-party build tools or multi-file projects. A table can continue playing an installed revision after the authoring VM shuts down. Guest actions still go through the room’s authorization checks.

Execution experiment

What can a rule actually do?

A third experiment runs compiled WebAssembly in a fresh Node worker. The module receives one integer and returns a proposed next value for a six-segment clock. The host decides whether to accept it. 

node scripts/gizmos-research/clock-wasm.mjs

Observed in the local run. The increment rule proposed 4 from 3. From 6 the same rule proposed 7 and the host rejected it. A fixture requesting an import was denied, as was a module declaring private linear memory. The host terminated a non-returning fixture at its 1.5-second wall-clock deadline.

This fixture runner accepts a deliberately narrow subset of Wasm, limits modules to 512 bytes and contains no upload endpoint. Startup and compilation count toward its approximate deadline. Node worker threads share a process and do not establish a hard memory ceiling for each tenant. Before opening execution to third-party code, repeat this test in a hardened service with measured resource limits, versioned inputs and server-side action authorization.

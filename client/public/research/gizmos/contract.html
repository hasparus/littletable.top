Gizmo specification · proposal for PR #59

What runs at the table?

A player forks the tarot deck so that The Tower rumbles when it lands. Another brings their Owlbear initiative tracker. The owner installs each once, and everyone can play. Neither author needs a Little Table release.

The following is a proposed contract. The playable PR currently implements the marketplace, requests, drawer and host-rendered pieces. The first executable release has three acceptance gates below.

What the owner installs

The owner installs a Gizmo for one board. Each placed prop gets its own saved state. Two decks from the same edition can have different cards on top.

  1. Browse or request. The repository registry supplies a small static thumbnail, a name and a source link. Browsing and player requests fetch zero mod code. Anyone can request a listed Gizmo, an unlisted public GitHub folder or a direct manifest URL. The owner receives a modal and can defer or decline.
  2. Resolve for installation. Once the owner starts installation, resolve a GitHub ref to its full commit. Accept a folder containing index.html, rules/, or an Owlbear v1 manifest.json. Also accept the Owlbear manifest URL copied from its store, including HTTPS URLs outside GitHub. For hosted Owlbear installs, keep the manifest URL. Resolve panel and background entries against that URL and let each page load assets from its own document base. Offer a choice when a folder contains both a native app and an Owlbear entry.
  3. Review and install. For a native GitHub package, show the commit and artifact digest. For a hosted Owlbear link, show the publisher’s hostname, the manifest link and the warning below beside the Install button. Show requested access in both cases. Recheck board ownership when saving the installation. For a live link the receipt records the source URL and approved grants.
  4. Play. Before the first install, the Gizmos menu opens the marketplace. Installation opens the quiet white drawer already scrolled to the new piece. All participants can use an installed Gizmo. Drag, tap or keyboard-place a native prop. An Owlbear action opens its original panel from the drawer. An extension with a background entry gets one background context per connected participant per board, independent of panel opens. The tldraw sidebar carries the gallery launcher.

This extension updates automatically. Future code from this publisher will run in your players’ browsers without another prompt. If the publisher or their hosting is compromised, an update could read or change board data the extension can access. You can disable it at any time.

For hosted Owlbear links, revalidate the live manifest when a participant opens or reloads the board. Load its current background and panel entries from the publisher. An ordinary code or asset update runs with the existing grants, even if the manifest version stays the same. Additional permissions require separate approval before the extension can use them. If the source is unavailable, show the failure on that Gizmo and let the table continue playing.

Use browser conventions for native packages. A public GitHub folder with browser-ready files needs no dedicated author manifest. An optional Web App Manifest can provide the title, icons and start URL. Little Table generates an internal install receipt describing entries, files, hashes and grants. Existing gizmo.json links continue to resolve their original pinned pieces. Official successors live in top-level gizmos/ and go through the same installer as a player's fork. Web App Manifest

Put the Gizmo on the board

Placeable tldraw shapes are the default. Draw an arrow from the Spotlight rail to a note, group them, and move them across the map. The arrow follows the rail and the names stay in order. Drop a second rail for a different party.

Tarot decks and each dealt card, both Spotlight widgets, the initiative rail and the explosion button belong on the canvas. The host creates a stable shape ID, page and parent, bounds and transform for each placed object. The renderer draws inside those bounds. An arrow binds to the shape ID, so edits, reconnects and renderer reloads preserve the connection. Selection, multiselect, move, rotate, grouping, ungrouping and z-order use the ordinary tldraw tools. Group transforms apply to the prop and its hit area together.

The select tool can operate the prop’s controls or move it by its body. With the arrow tool, the same controls are part of the board target. Pointing an arrow at the red button must never set it off. Copying a prop creates a new instance with independent state under its package’s duplication policy. A duplicate deck must never acquire the source deck’s private draw pile. A disabled renderer leaves a selectable placeholder with the same geometry and attachments.

Panels and background services are appropriate for board-wide utilities, including Owlbear extensions that only declare a popover or background page. They can operate on scene objects through granted SDK calls. A utility needs no invisible shape just to run.

Acceptance test. Place a widget, bind an arrow using the arrow tool over a control, and group the widget with another shape. Move the group and ungroup it. Check that the endpoint still follows the same shape and the widget still works. Repeat after another participant joins and after reloading the shared board.

A native Gizmo owns its canvas

TypeGPU and TypeGPU Kit run in the participant's browser. A mod author owns the shaders, artwork, sound and pointer response. Little Table supplies placement, coordinates, focus and the connection to the room. 

gizmos/tarot/
  index.html            browser entry
  dist/table.js         built TypeScript and TypeGPU shaders
  art/                  card faces and backs
  rules/                optional PsychoScript actions

Plain HTML and JavaScript can run as committed. TypeScript authors can commit a ready build or publish a versioned artifact tied to the source commit. A Workshop build is a third way to produce those same bytes. Resolve dependencies and apply the TypeGPU transform at build time. Install a fixed output digest. Keep repository build scripts in a disposable build environment, with no board access or publishing credentials.

Mount each visible instance in an isolated HTTPS frame on a dedicated mod origin with a canvas and an instance-scoped SDK connection. Scope asset URLs and storage so another installation cannot use them. During a drag the host supplies zoom-correct board coordinates, pointer capture beyond the frame, cancellation and screen-to-board transforms. The renderer owns the animation loop. Commit the semantic drop and final pose once. Other clients can interpolate from the same flight inputs. Suspend offscreen renderers, release GPU and sound resources on teardown, and restore from room state.

Two Spotlight widgets

Rail. A vertical rail holds editable name strips. Drag any strip to another position, or focus its grip and use the up and down arrows. The brass marker stays with the selected name when the order changes. Try the rail

Sliders. Stack one horizontal slider per name. Each metallic thumb clicks into visible stops. Moving one changes just that person’s level. The prototype uses eleven positions from 0 to 100. All participants share the order and levels. Try the sliders

Official Tarot and the Spotlight rail and sliders must preserve their interactions on that path. Start sound after a user gesture, respect local mute and reduced motion, and make screen shake a bounded host effect. PsychoScript owns the house rule

An author can ship a standalone rule or pair rules with a visual Gizmo. For instance, a separate round counter can run a rule when someone advances it.

The filename rules/advance.js declares an action called advance. A rules-only install gets a labeled action in the drawer. A web Gizmo can invoke that action on its own instance through the SDK. Each action runs plain JavaScript in a fresh PsychoScript VM in an isolated runner. The room supplies an actor-filtered snapshot via a host function and validates the returned JSON as a proposed next state. A rule can compute with ordinary JavaScript. Add named typed tools as needed for private state and post-commit effects. Keep graphics objects in the browser renderer. 

// rules/advance.js
const { speaker, turns } = await read();
return { speaker, turns: turns + 1 };

Measured. With published psychoscript@0.3.0 on Node 26.13.1, this exact rule, given Mira and two turns through Host.fn, returned Mira and three turns. That checks rule syntax and host calls. Before choosing a production runner, verify the package on Cloudflare or deploy a separate process on a supported runtime. The upstream package lists Node and Bun. Published package · VM contract and execution limits

Expose only the tools granted for this installation and actor. Limit active time, wall time including tool waits, calls, output and state size. The interpreter's timeout operates between VM steps and its output limit covers returned text and logs. Enforce memory and termination outside the VM. A failed or cancelled run discards its proposal and staged effects. In the first release rules run to completion per action. Persisting suspended VMs across upgrades would require interpreter-version pinning and deduplicated host calls.

Who can change the board?

The owner authorizes arbitrary mod code to run in participants' browsers. A participant using it retains their own role. Shared writes go through Little Table's authenticated host. The room checks the active installation, actor, grants, board and instance on every command. Never hand frames session cookies, board passes, provider tokens or the secret-layer document. Give privileged browser features and external data access explicit, reviewable grants. Native packages bundle their executable dependencies. Hosted Owlbear extensions load the publisher’s current code. Network access for data can disclose whatever the mod can read, which belongs in the owner's review.

Give native packages instance-local read and write access by default. Package authors can record additional requested board grants at publication, or ask through the SDK at runtime. A direct-link edition starts with the same defaults. A new grant opens a host-owned owner review before use. A refusal returns a typed error to the author. The room enforces filters when reading as well as writing. Isolate framed content on a separate site from board authentication, validate message schemas, restrict network and navigation in host policy, and keep a host-controlled disable action available if a mod stalls. The browser owns GPU scheduling. Owner approval cannot guarantee frame time, prevent device loss or recall data a participant has already received.

A proposed SDK v1 exposes placement and instance lifecycle, filtered read/subscribe, instance commands and transient effects. A native web app can publish its own state changes with instance-write access, even without a rule. Trusted shared decisions such as hidden draws use room-private state and an authorized rule or host service. The Owlbear adapter may also request role-filtered scene items and namespaced metadata writes. Browser code can observe everything delivered to it, including preloaded art. Batch-warm public faces when hidden identity matters. Keep the chosen identity and order private until the authorized reveal.

Each durable command carries an instance, expected state revision and request ID. The room validates the result and atomically commits state, effect receipt and next revision. Identical retries get the recorded result. Stale edits get a conflict and fresh view. Concurrent draws cannot consume the same card twice. Send springs and sound as local presentation or deduplicated events. A rejoining client reconstructs the current pose and face without replaying yesterday's explosion. On uninstall revoke channels, stop contexts and subscriptions, and offer the owner a snapshot for recovery.

Three gates for this PR

  1. Port the tarot with its feel intact. Record the current deck as the reference. A slow drop near the deck leaves a loose face-down card. A fast toss from the deck reveals the real face in flight, rotates within −3° to +3° in the table plane and coasts to rest. Tapping a loose card flips either way. Moving it preserves its face. Rapid taps deal to the three-column grid. Warm and decode art in time for the turn. Compare touch, mouse, keyboard, reduced motion and GPU loss. Re-run the existing browser and room tests against the installed package. Open a saved board and confirm its card IDs, order, face, poses and remaining pile survive migration. Keep the installed legacy edition available until the owner approves upgrading. Current browser fixtures
  2. Fork a behavior mid-campaign. Install a player-authored round counter from another GitHub repository. Fork its PsychoScript action to advance by two rounds. Have a player request the revised edition, an owner approve it, and two clients use it on an existing deployment. Verify one advance under a retry, independent second-instance state, a failed rule leaving the previous count intact, and rejection of a stale grant after uninstall.
  3. Play through the original Owlbear tracker. Use its original release code with no extension-source edits. From a GM and a player browser, add a token via its context menu, set initiative, advance, select and focus a row, close and reopen, reconnect and verify the same order and role visibility. Inspect the network trace for zero extension-code requests on marketplace browse. Change the hosted panel and background code at the same URL with the same manifest version. Reopen the board on both clients and verify the update arrives without another install prompt. Request a new permission and verify it remains unavailable until approved. Disable the link and verify existing frames lose board access. Publish the result per fixture. Merely opening its panel passes only the loading test.

A renderer decision worth a trial. For heavy native props, compare an isolated frame per visible prop with one shared renderer per installed edition. The former is simpler to isolate and dispose. The latter could share a GPU device and art across a spread. Measure pointer-to-frame latency, frame time and memory on the same phone and desktop using the current tarot as baseline before choosing the renderer granularity.

Choose where to build

One active authoring path per Little Table user. Both paths produce the same immutable release and can suggest it to a table owner. Receiving, installing and playing a Gizmo are available independently of that choice.

Publish from your own agent with MCP

Mira asks her agent to fork the round counter and change the increment. She authorizes Little Table to let that client work on her draft. The agent can rehearse a sample turn, show her the proposed release, publish it to the audience she selects and return a link. This path needs no Workshop account connection or provider token at Little Table.

  • fork_release(parentDigest) creates a private draft tied to the authenticated author. A repeated request with the same key returns the same draft.
  • read_draft, edit_draft and rehearse_draft operate on an authorized draft ID. Edits supply the expected revision. A stale edit returns a conflict and the current revision. Rehearsal uses a fixture and returns a bounded result.
  • prepare_release validates the package and returns its digest, parent, asset credits, permission diff and proposed audience. publish_release needs scoped publish access and the author’s confirmation bound to that digest and audience. Use a Little Table consent page when the client cannot reliably collect that confirmation. Retrying returns the same release.
  • propose_install sends one known board a review link if the caller can propose there. For an owner using an agent, approval in the board can complete the install. For a player, it goes to the owner. A package description, tool annotation or model-generated “approved” field carries no authority.

The remote MCP service exposes protected-resource metadata. On each call it checks the access token’s issuer, audience, expiry, authoring mode, granted scope and access to the requested object. A token for a provider, another resource or another draft cannot authorize the call. Publish consent is separate from connecting a client. MCP authorization · MCP security guidance

Build and publish inside the Workshop

Mira forks the tracker in her browser, edits it herself or asks a coding agent to revise it, and tries the player and owner seats. The Workshop shows the same proposed release and publishes it on her confirmation. Its backend uses the same validation and release operations directly. There is no MCP client setup in this path.

Give each build job an expiring lease for one draft revision and a disposable workspace. Mount the package, catalog and synthetic fixtures. Keep live board passes, cloud credentials and provider tokens outside the build environment. Broker model calls from the trusted host. Limit build time, output size and spend. Discard temporary files and cancel outstanding work on disconnect. Treat imported descriptions, source and build output as untrusted content, including when an agent reads them.

If an author switches paths

Offer “Switch authoring method” outside the build flow. Confirm the change, increment the author’s mode generation, revoke prior write and publish grants, cancel builds and invalidate outstanding release confirmations. Preserve the saved draft and published editions. Check the generation again when a queued job writes back or publishes, so a late completion cannot overwrite edits made through the new path. Fresh consent enables the other path. No switch is needed to open someone else’s install link.

Who pays for the build?

MCP authors pay through the agent they already use. The Workshop has a separate product choice about model access.

Author-funded Workshop. OpenAI documents identity sign-in and separately authorized ChatGPT plan usage for eligible inference. The open-source/local flow has its own client requirements. A remotely hosted or paid Workshop must establish eligibility with OpenAI. Anthropic requires prior approval to offer Claude account login or subscription limits in a third-party product. Little Table’s eligibility is unverified for both hosted integrations. OpenAI sign-in and scopes · Hosted availability · Anthropic Agent SDK authentication

Little Table-funded Workshop. Little Table could use its own provider API account. Show who pays before the build, reserve a per-job budget, count retries against it and stop on exhaustion. A denied grant or exhausted personal allowance returns the draft for manual editing. Charging the product account requires a separate, explicit choice.

For approved user-funded access, establish the Little Table session from verified identity and link it to the correct local account. Store the separate inference grant encrypted on the trusted host, keyed by author, provider and workspace. Check scope and expiry before each model call. Revoke or delete the connection on disconnect, stop new calls and drop pending work. Logs retain usage totals and opaque job IDs. Prompts, access tokens and secret board data stay out of logs, packages and runtime bindings. Installed editions use ordinary table actions after the author disconnects.

What travels with a fork?

For a native release, the installer records an internal receipt with the host API version, executable entries, state schema, requested capabilities, locked dependencies, asset credits and hashes. The registry records the authenticated publisher, parent release digest, license and visibility. It assigns the official badge only to the Little Table publisher.

Compute a digest over the canonical receipt fields and its content-addressed code and assets. Verify every blob before preview or execution. Refuse missing assets, unsupported APIs and oversized packages. Serve assets from immutable storage. A fork copies the redistributable definition with attribution and starts with fresh instance state. Private draws, live seat names, room identifiers and agent conversations stay with their original table or author.

Link sharing lets a friend try an unlisted edition. Anyone holding the link can forward it. A curated shelf adds discovery and a review queue. Open publishing needs reporting, moderation and an identifiable publisher for every revision. A listing can show a static preview without running package code. Delisting removes discovery. Quarantining a dangerous digest also blocks installs and pauses affected instances at their next action, including installs reached by link. Allow an owner to recover their state.

For native release updates, bind owner consent to the board, expected installed revision, proposed digest, visibility and capability diff. Recheck ownership, revocation and digest in the commit path. An update needs fresh review. Stage any state migration against a snapshot and atomically commit the new edition and migrated state together. On failure keep the current instance playable. A later rollback restores a compatible snapshot and tells the GM which intervening actions would be lost.

What would prove it?

My preference for the first trial is MCP publishing if the people at the table already use coding agents. One player can publish the counter fork and another GM can install it without Little Table holding a model credential. If the intended author only uses their phone during prep, I’d test the Workshop with the same brief instead. Measure whether they can get a second table playing the fork unaided and explain who can change it.

Run the local contract experiment with node scripts/gizmos-research/release-contract.mjs. It models the two points at which stale authority matters: publishing after an author changes paths and installing after an owner’s review becomes stale. It uses synthetic records. It exercises neither OAuth nor a deployed sandbox.

  • Two independent authors. Give one MCP access and the other Workshop access. Each can finish a release in their own path. A grant for one author cannot read or modify the other’s draft. After switching paths, late jobs and old publish confirmations fail.
  • One player and one owner. A player proposes; only the current owner can install. Change the release or the installed base between review and apply. The owner must see a new diff. Publishing a new native edition leaves existing native installations pinned.
  • Two clients and one room. Retry a draw after a simulated connection loss. Verify one card, one state advance and the same result for the retry. A guest observes only the revealed card. Exercise the GM’s separate room and a reconnect.
  • One broken release. Try an incompatible migration, a failed build, a revoked inference grant and a quarantined edition. Verify no partial install, no unapproved billing fallback and an owner recovery path. Run deployment-level isolation and resource checks before admitting arbitrary code.
